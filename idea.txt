Great video, but strictly speaking, this isn't production-ready according to Richardson's Microservices Patterns. You have a critical Dual Write issue in the Auth Service: committing to the DB and then publishing to RabbitMQ separately creates a consistency risk if the process crashes. You need the Transactional Outbox pattern here. Also, a shared INTERNAL_API_TOKEN is a security vulnerability compared to mTLS, and you're missing Distributed Tracing (correlation IDs), which makes debugging impossible in prod. The shared library also creates tight coupling, effectively making this a distributed monolith.

vi is Vitest’s utility object (like Jest’s jest), used for mocking and spying.

Common vi APIs:

vi.fn() creates a mock function
vi.mock() mocks a module
vi.spyOn() spies on existing methods
vi.hoisted() creates values that must exist before vi.mock is evaluated
You wrote vi.hosted in your question; the correct one is vi.hoisted.

Why vi.hoisted is used
vi.mock(...) is hoisted to the top by Vitest.
So if your mock object is declared normally below, it may not exist when the mock factory runs.

vi.hoisted(() => ({ ... })) guarantees those mock refs are created early enough for module mocking.

import { describe, expect, it, vi } from 'vitest';
import { HttpError } from '@chatapp/common';

const messageRepositoryMocks = vi.hoisted(() => ({
    create: vi.fn(),
    findByConversation: vi.fn(),
}));

const conversationServiceMocks = vi.hoisted(() => ({
    getConversationById: vi.fn(),
    touchConversation: vi.fn(),
}));

vi.mock('@/repositories/message.repository', () => ({
    messageRepository: messageRepositoryMocks,
}));

vi.mock('@/services/conversation.service', () => ({
    conversationService: conversationServiceMocks,
}));

import { messageService } from '@/services/message.service';

describe('messageService', () => {
    it('creates message when sender is a participant', async () => {
        conversationServiceMocks.getConversationById.mockResolvedValue({

Quick explanation before I finalize:

Why normal pattern fails
Today, business data commits in DB, then event publish happens separately. If DB commit succeeds but Rabbit publish fails/crashes, state changes but no event is emitted. That creates cross-service inconsistency.

What outbox fixes
Write both business change + event record in the same DB transaction. A worker later publishes from outbox. If broker is down, event stays in DB and retries until published.

Publish semantics

At-least-once + dedupe: event may publish more than once; consumers ignore duplicates using eventId.
At-least-once only: duplicates may cause repeated side effects.
Exactly-once: expensive/complex in distributed systems.
Rollout options

Flagged dual-path: safest migration; feature flag controls cutover.
Hard cutover: simpler, higher risk.
Shadow mode: publish both temporarily to compare behavior.
