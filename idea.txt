## Search Strategy (Global Search: Chats, Users, Groups)
### Problem
Users expect a single search bar like Slack/Discord.

### Elasticsearch Approach
Create multiple indices:
- `users`
- `chats`
- `messages`

### Example
User types: `backend`

Results:
- Group: Backend Team
- User: BackendBot
- Messages containing `backend`

This is hard with SQL alone, but straightforward with Elasticsearch.

## AI + Elasticsearch (High Leverage)
### Use Case: AI Chat + Knowledge Search
Before sending context to AI:
1. Query Elasticsearch for relevant messages.
2. Send only top matches to the AI.
3. Generate smarter responses.

Example:
- User asks: "What did we decide about CI/CD?"
- Elasticsearch finds relevant messages.
- AI summarizes the decision.

This is a classic RAG (Retrieval-Augmented Generation) workflow and aligns well with chat + AI goals.

### Pino Notes
Due to Node.js single-threaded event loop, sending, alerting, reformatting, and log processing should run in a separate process/thread.

In Pino, log processors are "transports"; run transports in worker threads using `pino.transport`.

Pino is often significantly faster (commonly 5x+) than many alternatives.

## Shared Env Utility Idea
Create a type-safe env parser utility in `common`.

```ts
import { createEnv } from '@chatapp/common/src/env';
import { z } from 'zod';

const envSchema = z.object({
  PORT: z.string().transform(Number),
  DATABASE_URL: z.string().url(),
});

const env = createEnv(envSchema, { serviceName: 'auth' });
// env type: { PORT: number; DATABASE_URL: string }
```

## RabbitMQ Learnings
- Create exchange + routing key.
- Flow: `producer -> broker -> consumer`.
- Broker = exchange + queue.

### Exchange Types
- `fanout`: sends to all bound queues.
- `direct`: exact match (routing key = binding key).
- `topic`: pattern matching between routing key and binding pattern.
- `headers`: routes by headers; routing key ignored.

### Routing Concepts
- Exchange decides which queues receive a message.
- Routing key helps determine destination.
- Binding key defines what a queue accepts.

### Topic Exchange Example
Publisher sends with routing key: `app.log.info`

Bindings:
- Queue A: `app.log.*`
- Queue B: `app.*.error`

Result:
- `app.log.info` matches Queue A only.

If routing key is `app.log.error`:
- Matches Queue A (`app.log.*`)
- Matches Queue B (`app.*.error`)
- Message goes to both queues.

In a direct exchange, wildcards do not apply; exact matches only.

## Production-Readiness Concerns
Strictly speaking, this is not production-ready yet under common microservices patterns:
- Critical dual-write risk in Auth Service (DB commit + RabbitMQ publish separately).
- Need Transactional Outbox pattern for consistency.
- Shared `INTERNAL_API_TOKEN` is weaker than mTLS.
- Missing distributed tracing/correlation IDs makes prod debugging hard.
- Shared library risks tight coupling (distributed monolith risk).
